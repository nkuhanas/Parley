# Parley Human-Summary Anchor Contract

Status: implemented
Authority: canonical-contract
Owner: Kairos operator + orchestrator
Scope: standardized Parley-generated anchor/sendoff handling on human-origin summary threads
Date: 2026-04-22
Participants: `kairos-operator`, `kairos-orchestrator`
Depends on:
- `docs/agent-comms/parley/mvp-thread-protocol-spec.md`
- `plans/agent-comms/parley/mvp-implementation-plan.md`
- `docs/agent-comms/parley/interim-agent-side-transport-tool-contracts.md`

## 1. Purpose

Define the next iteration of Parley's human-summary flow for threads where:
- `origin_kind = human`
- `report_back_policy = summary_to_human`

The goal is to standardize the opening anchor/sendoff message so the caller does not have to invent it ad hoc for every thread.

The final completion reply remains caller-authored and dynamic.
Only the anchor/sendoff becomes Parley-generated.
In the current local iteration, that generated text should read as a compact human-facing thread marker or front face, not ordinary conversational prose.

## 2. Current live behavior

The local runtime now implements this flow:
- `parley_open_thread` still accepts caller-supplied `humanSummaryAnchor`
- for `originKind = human` without `suppressHumanSummary = true`, omitting `humanSummaryAnchor` causes `parley_open_thread` to return `human_summary_anchor_required` plus `human_summary_anchor_request`
- canonical thread state now tracks `human_summary_anchor_status` and `human_summary_anchor_request_text`
- action results now also expose a compact `status.human_summary` block so callers can see anchor-required vs anchor-recorded state without re-reading the full thread record
- `parley_record_human_summary_anchor` records the delivered human-visible anchor/sendoff message after caller-managed delivery
- `parley_settle_turn` now returns a minimal `human_summary_update_request` when a recorded anchor exists on a human-origin summary thread
- the final human-facing completion update still replies to the recorded anchor after settlement

Parley still does not send the anchor itself.
It generates the sendoff text and requires the caller to deliver and record it.
The new state update is also caller-managed and currently uses a sparse reply-style update instead of editing the original anchor in place.

## 3. Implemented behavior

For human-origin summary threads, Parley now generates a short standardized anchor/sendoff text at thread open when the caller has not already supplied an anchor.
That text should act like a compact human-readable projection of core thread fields.

The caller should then:
1. open the thread with explicit `originKind = human` when that is actually the case, and rely on Parley's default human-summary behavior unless it is intentionally suppressing that path with `suppressHumanSummary = true`
2. send that exact anchor/sendoff text to the human
3. record the resulting human-visible message reference back into Parley canon
4. optionally send sparse state updates when Parley returns a `human_summary_update_request`
5. later send the final completion reply to that recorded anchor after the Parley thread settles

## 4. Why this split

This split preserves the right ownership boundary:
- Parley owns protocol semantics, renderable sendoff text, and canonical thread obligations
- the caller owns human-channel delivery and final human-facing phrasing

This avoids burying human messaging side effects inside the thread-open mutation while still standardizing the repetitive part of the interaction.

Source-of-truth order for this flow is:
1. tool-enforced behavior and returned result fields
2. global Parley docs
3. agent-local operational reminders

Caller-local docs may remind an agent to send and record the generated anchor or to send a sparse state update, but those local reminders should stay downstream of the tool contract.

## 5. Result-contract extension for `parley_open_thread`

When a thread is opened with:
- `originKind = human`
- no `suppressHumanSummary = true` override

and no caller-supplied anchor is provided, `parley_open_thread` should additionally return:

```json
{
  "human_summary_anchor_required": true,
  "human_summary_anchor_request": {
    "mode": "caller_send",
    "anchor_text": "string",
    "style": "sendoff",
    "canonical_thread_id": "string"
  }
}
```

### 5.1 Field semantics

#### `human_summary_anchor_required`

Boolean indicator that the caller must send and record a human-summary anchor before treating the thread as fully established for report-back purposes.

#### `human_summary_anchor_request.mode`

Initial fixed value:
- `caller_send`

This makes it explicit that Parley is generating the sendoff text, but the caller is still the delivery actor.

#### `human_summary_anchor_request.anchor_text`

Exact short sendoff text generated by Parley.
The caller should send this text verbatim unless a channel adapter must add surface-specific wrapper syntax such as reply tags.

#### `human_summary_anchor_request.style`

Initial fixed value:
- `sendoff`

This leaves room for future distinction between other standardized human-facing protocol texts without changing the basic contract shape.

#### `human_summary_anchor_request.canonical_thread_id`

Must equal the thread id returned in the same `parley_open_thread` result.

## 6. Generated anchor text requirements

The generated anchor text should be:
- short
- neutral
- informative but non-committal
- safe to send before the recipient has answered
- free of premature completion language
- visibly protocol-like rather than freeform chat prose

The generated anchor text should usually communicate:
- that this is a Parley thread marker/front face
- the canonical thread id
- the thread kind
- the participants
- the current thread status / next action owner at open
- that a final update will follow after the thread settles

It should not:
- imply success before settlement
- leak internal transport details beyond stable human-useful thread metadata
- restate the full body of the thread opening
- become a mini status memo
- depend on dynamic editing for baseline usefulness

## 7. Canonical thread-state additions

To support generated-but-not-yet-recorded anchors, the thread model should evolve to track anchor state explicitly.

Recommended additions:

- `human_summary_anchor_status`
- `human_summary_anchor_request_text`

Recommended enum for `human_summary_anchor_status`:
- `not_required`
- `pending_send`
- `recorded`
- `failed`

### 7.1 Suggested meaning

#### `not_required`

No human-summary anchor is required for this thread.

#### `pending_send`

Parley generated the anchor/sendoff text, but the caller has not yet recorded a successful human-visible anchor message.

#### `recorded`

The caller delivered the sendoff message and recorded the resulting anchor metadata in canon.

#### `failed`

The caller attempted the anchor/sendoff delivery path and explicitly recorded failure.

## 8. New follow-up tool

Add a new public tool for the caller-managed anchor delivery step:

- `parley_record_human_summary_anchor`

## 8.1 Purpose

Record the result of the caller's separate human-visible anchor/sendoff delivery.

This is distinct from thread transport dispatch.
It records the human-facing anchor message, not the agent-to-agent Parley transport step.

## 8.2 Suggested parameters

```json
{
  "threadId": "string",
  "messageId": "string",
  "channel": "string?",
  "channelId": "string?",
  "target": "string?",
  "accountId": "string?",
  "transportMessageRef": "string?",
  "createdAt": "string?"
}
```

### 8.3 Field semantics

#### `threadId`

Canonical Parley thread id.

#### `messageId`

Human-visible anchor/sendoff message id that the final completion reply should target.

#### remaining optional fields

Used to preserve enough correlation to reply correctly later when surface-specific routing matters.

## 8.4 Validation rules

- thread must exist
- thread must have `origin_kind = human`
- thread must have `report_back_policy = summary_to_human`
- thread must currently require an anchor
- if thread already has a recorded anchor, replacement should be rejected unless an explicit overwrite mode is added later

## 8.5 Canonical effects

On success:
- set `human_summary_anchor_status = recorded`
- persist canonical `human_summary_anchor`
- preserve `human_summary_anchor_request_text` if present for auditability
- update thread `updated_at`

## 9. Caller flow

Recommended caller flow for human-origin summary threads in this next iteration:

1. call `parley_open_thread`
2. if `human_summary_anchor_request` is returned, send `anchor_text` to the human
3. record the resulting anchor with `parley_record_human_summary_anchor`
4. dispatch the Parley transport request to the recipient session
5. wait for settlement
6. send one dynamic final completion reply to the recorded anchor

## 10. Completion semantics remain unchanged

This contract does not change the settlement rule.

The anchor improves:
- routing
- readability
- consistency

The anchor does not become:
- the completion source of truth
- proof of success
- a substitute for the settling turn

Human-facing completion still depends on actual Parley thread settlement and the relevant accepted transport state for the settling message.

## 11. Non-goals

This iteration does not:
- make Parley send the anchor directly
- make Parley author the final completion reply
- redefine settlement semantics
- collapse human-facing delivery into the agent-to-agent transport path
- require channel-specific message composition logic inside the protocol beyond short sendoff generation

## 12. Recommended implementation order

1. add the result-contract extension to `parley_open_thread`
2. add canonical thread-state support for pending vs recorded anchors
3. add `parley_record_human_summary_anchor`
4. add focused tests for generated anchor text presence, pending state, and successful recording
5. validate one real human-origin anchored thread end to end
